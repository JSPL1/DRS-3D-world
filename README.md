# DRS 3D WORLD

**3D Printing & Innovation — Bhubaneswar, Odisha**
*Bringing your ideas to life, one layer at a time.*

A full-stack Next.js 15 application: a cinematic marketing site with a scroll-driven
Three.js printer teardown, an STL quote calculator that prices real geometry, and an
enterprise CMS behind JWT auth with five roles — all on SQLite, deployable as a single
Render service.


there is no migration step to run.

## What's in it

### The hero

`/` opens on a procedurally-built 3D printer — no downloaded model, every part
constructed from primitives. Scrolling drives a single timeline
(`components/three/printer/Choreography.tsx`):

1. **Boot** — chamber lights, display backlight, nozzle heats, fans spin up, gantry
   runs a four-corner calibration pass.
2. **Teardown** — all 28 components separate outward on a staggered schedule, each
   captioned as its group scrolls past.
3. **Reassembly** — the machine puts itself back together.
4. **Production run** — six products print in sequence, layer by layer.

The layer reveal is the neat part: the nozzle never moves vertically. A world-space
clipping plane sits at the nozzle tip and the *bed descends* as the part grows —
exactly how a bed-drop printer works — so no geometry is rebuilt per frame.

Reduced-motion is honoured throughout: Lenis smooth scrolling and the custom cursor
both switch off.

### Quote calculator

`/quote` parses binary **and** ASCII STL in the browser — the customer's geometry
never leaves their machine, only the derived measurements are submitted. It computes
signed-tetrahedron volume, surface area, bounding box and triangle count, then prices
material, machine time, labour, electricity, margin, GST and delivery as separate
lines.

Verified against solids with known values: a 10 mm cube parses to exactly 1000 mm³
and 600 mm². Non-watertight meshes and flipped normals are detected and flagged
rather than silently mispriced, and the server recalculates independently of the
browser figure.

### Admin CMS

`/admin` — dashboard, analytics, products (full CRUD, 40+ fields), orders,
quotes, leads, categories, brands, coupons, homepage builder, banners, blog, gallery,
videos, testimonials, reviews, FAQ, users, notifications, activity log, SEO and
backup.

### Auth

JWT via `jose` (Edge-compatible, so middleware and route handlers share one
implementation). Login, forgot-password, 6-digit OTP, reset, remember-me, session
timeout, and per-permission RBAC. Sessions are re-validated against the database on
every request, so suspending an account takes effect immediately rather than at token
expiry. A password reset bumps `token_version`, invalidating every issued token at
once.

## Deploying to Render

The repo includes `render.yaml`. Push to GitHub, then **New → Blueprint** in Render
and point it at the repo.

Set these two yourself (marked `sync: false`):

- `NEXT_PUBLIC_SITE_URL` — your real domain, so canonical tags, Open Graph and the
  sitemap are absolute.
- `SEED_PASSWORD` — set before the first deploy.

`JWT_SECRET` is generated by Render automatically. Changing it later signs everyone out.

### ⚠️ The one thing that will bite you

**Render's free plan has no persistent disk.** `render.yaml` declares a 1 GB disk at
`/var/data`, which requires a paid instance. On the free plan the SQLite file lives on
ephemeral storage and is **wiped on every deploy and restart** — the app re-seeds
itself and any real orders, quotes and leads are gone.

Free tier is fine for a demo. For anything real, either keep the disk, or point
`DATABASE_PATH` at a hosted SQLite service such as Turso.

Take backups from `/admin/backup` — it uses SQLite's own backup API, so the snapshot
is consistent even while the site is serving traffic.

## Notes for whoever picks this up next

- **Images** are generated on the fly by `/api/tile` as on-brand SVG. There are no
  binary assets in the repo. Swap the stored URLs for real photography and everything
  else keeps working.
- **Email** is a logging stub in `lib/mailer.ts`. OTP codes print to the server
  console; in development they are also returned in the API response so the flow is
  testable. Wire a provider into `deliver()` and nothing else needs to change.
- **Chart colours** are validated for colour-blind separation against the admin's dark
  surface. If you change them, re-run the validation — brand orange at its lighter
  steps fails the lightness band. See the note at the top of `components/admin/Charts.tsx`.
- **Rate limiting** is per-process and in-memory. It suits a single Render instance;
  scaling horizontally needs shared storage.
